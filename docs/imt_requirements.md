# IMT (Importance-Map Transport) 実装要件書

- 版: v0.4 (draft) — KEYFRAME_NACK(type=4) と1回限定再送を追補
- 日付: 2026-08-25(初版 2026-06-11)
- 対象リポジトリ: `rp-stereocam`(コア+送信アダプタ)、`MetaPuppetVR`(受信アダプタ)
- ステータス: 実装着手前のレビュー用ドラフト

## 1. 目的とスコープ

低遅延ライブ映像伝送において、フレームごとの**重要度マップ**(タイル格子の uint8 重み)を
唯一の制御入力として、以下3つを統一的に駆動する純粋Cライブラリ `imt` を実装する。

1. 画質配分 — タイルごとの QP オフセット(ROI 符号化)
2. 誤り保護 — 重要度に応じた不均等 XOR-FEC
3. 送出順序 — 重要タイル優先のスケジューリング

加えて、受信側実測遅延をフィードバックとする **PI 型レイテンシ予算制御**を提供する。

### 1.1 スコープ外

- 重要度マップの生成(供給アダプタの責務。§4 の契約のみ規定)
- エンコード自体(x264 等はアダプタの責務)
- 1対多配信の実証(論文上は分析で扱う)
- 暗号化・認証

## 2. 設計原則(変更不可の制約)

- **R2.1** コアは VR・カメラ・コーデック・OS のいずれにも依存しない。
  公開ヘッダに Unity / D3D / libcamera / x264 の型が一切現れないこと。
- **R2.2** 定常状態でヒープ確保ゼロ。malloc は `*_init` のみ、解放は `*_destroy` のみ
  (`mpq_frame_assembler` と同じ流儀)。
- **R2.3** 定常パスは整数演算と LUT のみ。浮動小数点は init 時にのみ許可。
- **R2.4** すべての構造体は固定長・明示的フィールド。ワイヤ上は明示リトルエンディアン
  でシリアライズし、構造体の memcpy 送信を禁止する。
- **R2.5** 重要度マップは品質ヒントであり正しさに関与しない。
  マップ欠落・破損時は直前のマップ、それも無ければ一様マップに自動退化すること。
- **R2.6** C99、警告ゼロ(`-Wall -Wextra -Wpedantic` / MSVC `/W4`)、
  Pi(aarch64/GCC)と Windows(MSVC)の両方でビルド可能であること。

## 3. レイヤ構成

```
供給アダプタ(一様/中心/動き/マスク/タスク座標)
        │ ImtMap (uint8 タイル格子)
        ▼
┌─ imt コア ──────────────────────────┐
│ imt_map   : 格子定義・EMA・正規化              │
│ imt_qp    : 重み→QPオフセット LUT              │
│ imt_sched : 重要度降順の送出順序(計数ソート)    │
│ imt_fec   : XOR パリティ生成・グループ設計       │
│ imt_wire  : パケットヘッダ encode/decode        │
│ imt_packetize : フレーム→データグラム列          │
│ imt_assembler : 再構成+FEC回復(受信側)        │
│ imt_pace  : PI レイテンシ予算制御               │
└──────────────────────────────┘
        ▼
消費アダプタ(x264 ラッパ / UDP 送出 / pcvr_receiver 統合)
```

## 4. 重要度マップの契約

- **R4.1** マップはタイル格子。タイル辺長はコーデック由来のパラメータ
  (H.264 = 16、HEVC = 64 等)で、`cols = ceil(width/tile)`, `rows = ceil(height/tile)`。
  例: 2560×720, tile=16 → 160×45 = 7,200 タイル。
- **R4.2** 重みは uint8。0 は 1 として扱う。供給側は平均 ≈128 への正規化を
  推奨(SHOULD)、コア側は実測平均で再正規化するため必須ではない。
- **R4.3** 時間平滑化は整数 EMA: `w ← (w·(2^s − 1) + w_new) >> s`(既定 s=3)。
- **R4.4** マップ更新はフレームレート以下で可(既定 10 Hz)。更新が止まっても
  伝送は最後のマップで継続する(R2.5)。
- **R4.5** 一様マップ(全タイル 128)を与えたとき、システム全体の挙動が
  「ROI なし・均一 FEC・順序最適化なし」の通常伝送と一致すること(退化の検証)。

## 5. 配分の数式(規範)

- **R5.1** QP オフセット: `ΔQP(w) = round(−6·log₂(w̃/128))`、
  `w̃ = clamp(1, w·128/mean(W), 255)`、クランプ範囲 `[−6, +12]`。
  実行時は 256 要素 LUT 参照のみ(R2.3)。検証点:
  `w̃=128→0`, `w̃=255→−6`, `w̃=64→+6`, `w̃=32→+12`, `w̃=1→+12(クランプ)`。
  根拠: H.264 の QP+6 ≈ レート半減則とログ効用の比例配分閉形式解。
- **R5.2** FEC グループサイズ(小さいほど厚い保護):
  `w̃≥192→2`, `w̃≥128→4`, `w̃≥64→8`, `それ未満→16`。2 の冪のみ。
- **R5.3** 送出順序: タイル(またはスライス)重み降順。計数ソート(256 バケット、
  O(n)、安定)で実装すること。比較ソート禁止(R2.3 の精神)。

## 6. ワイヤフォーマット

- **R6.1** ヘッダは固定 40 バイト、リトルエンディアン:

| offset | size | field | 備考 |
|---|---|---|---|
| 0 | 2 | magic | "IM" (0x49 0x4D) |
| 2 | 1 | version | 1 |
| 3 | 1 | type | 0=SLICE, 1=MAP, 2=PARITY, 3=FEEDBACK, 4=KEYFRAME_NACK |
| 4 | 2 | header_size | 40 |
| 6 | 2 | flags | bit0=keyframe, bit1=codec_config, 残予約 |
| 8 | 8 | frame_seq | 単調増加 |
| 16 | 8 | capture_timestamp_ns | 送信側クロック |
| 24 | 4 | frame_size | フレーム総バイト数 |
| 28 | 2 | chunk_index | |
| 30 | 2 | chunk_count | |
| 32 | 2 | payload_size | このパケットのペイロード長 |
| 34 | 2 | fec_group | フレーム内グループ ID |
| 36 | 1 | fec_group_size | グループ内データパケット数 |
| 37 | 1 | fec_index | グループ内位置。0xFF=パリティ |
| 38 | 2 | reserved | 0 |

- **R6.2** チャンク分割は固定最大ペイロード(既定 1200 B)。最終チャンク以外は
  満杯とし、受信側が `frame_size` から各チャンク長を一意に再計算できること
  (パリティ回復時のサイズ曖昧性をなくすため)。
- **R6.3** MAP パケットのペイロードは
  `cols(u16) rows(u16) tile_size(u16) reserved(u16) + weights[cols·rows]`。
  1 データグラムで送る(7.2 KB → IP フラグメント許容)。フラグメント起因の
  欠落はマップ欠落として R2.5 で吸収する。
- **R6.4** (v0.3 改) FEEDBACK パケット(受信→送信の上り)のペイロードは 32 バイト:
  `latest_frame_seq(u64) latest_capture_timestamp_ns(u64) frame_age_ns(u64)`
  `frames_completed(u32) frames_incomplete(u32)`。
  `latest_capture_timestamp_ns` は完成フレームのキャプチャ時刻の**エコーバック**で、
  送信側はこれと自分の時計だけで遅延(上り分のバイアス込みだが一貫)を計算できる。
  `frame_age_ns` は受信側計測値(クロック同期がない場合 0 でよい)。
  送信間隔は受信側設定(既定 10 Hz)。
- **R6.4a** (v0.4 追補) KEYFRAME_NACK(type=4) は受信→送信の上り制御で、
  ペイロードを持たない40バイトヘッダのみとする。`frame_seq` に回復不能だった
  キーフレームのシーケンスを格納し、その他の可変フィールドは0とする。
- **R6.5** version 不一致のパケットは黙って破棄し、統計カウンタに記録する。
- **R6.6** 既存パケットのレイアウト・意味を変える非互換変更は、本書の版数と
  `version` フィールドの同時更新を必須とする。未知typeを旧受信側が黙って
  無視できる加算的なtype追加はversionを維持できるが、本書を改版し、
  `MetaPuppetVR` 側との適合テスト(§9)で同期する。

## 7. FEC(XOR パリティ)

- **R7.1** パリティペイロード = グループ内データペイロードの XOR
  (短いペイロードはゼロ拡張)。長さはグループ内最大ペイロード長。
- **R7.2** 受信側は「グループ内欠落がちょうど 1 かつパリティ受信済み」のとき、
  欠落チャンクをビット正確に回復すること。
- **R7.3** 回復不能(欠落 ≥2)のフレームは全棄却(現行 mpq と同じ latest-wins 方針)。
- **R7.4** パリティによる帯域オーバーヘッドの上限は設定可能とし、
  既定はデータの 12.5%(平均グループサイズ 8 相当)。

## 8. PI レイテンシ予算制御

- **R8.1** 入力: FEEDBACK の `frame_age_ns`(capture→受信完了)。
  出力: レートスケール `r`(Q16 固定小数、65536 = 1.0)。アダプタが
  エンコーダのビットレート/QP ベースに乗算する。
- **R8.2** 形: `e = (T − L)/T`(Q16)、`integ += e`(アンチワインドアップで
  クランプ)、`r = 1.0 + (kp·e + ki·integ)`、`r ∈ [0.1, 2.0]`。
  既定 `kp = 0.4`, `ki = 0.05`(Q16 定数)。64bit 中間演算。
- **R8.3** フィードバック途絶(> 1 s)時は `r` を 1.0 へ毎秒 10% ずつ復帰させる。
- **R8.4** 線形プラントモデルのシミュレーションで目標値へ単調収束し、
  振動が ±5% 以内に収まることをテストで示す。

## 9. テスト要件

- **R9.1** ハードウェア・ネットワーク非依存の単体テスト実行体 `imt_tests` を持ち、
  Pi と Windows の両方で全テストが通ること。最低限:
  - map: EMA 収束、平均正規化、一様マップ退化(R4.5)
  - qp: R5.1 の検証点全点、単調性(w̃ 増加で ΔQP 非増加)
  - sched: 計数ソートの降順・安定性
  - fec: 1 欠落のビット正確回復(R7.2)、2 欠落の棄却(R7.3)
  - wire: encode→decode ラウンドトリップ全フィールド一致、不正 version 破棄、
    header-only KEYFRAME_NACK の受理
  - assembler: ロス注入シミュレーション(欠落パターン網羅)でのフレーム完成率、
    不完全キーフレーム通知、KEYFRAME_NACKによる映像状態非破壊
  - pace: R8.4 の収束
- **R9.2** リポジトリ間適合テスト: 送信側でパケット化したバイト列を
  `MetaPuppetVR` 側のベンダリングヘッダでデコードして一致させる
  (`tools/abi_smoke_test` と同型の仕組み)。
- **R9.3** マイクロベンチ: 160×45 マップの EMA+正規化+QP 配列生成+順序生成の
  合計が Pi 4 実測で 100 µs 未満であること(論文のオーバーヘッド主張の根拠)。

## 10. 受け入れ基準(このフェーズの Done 定義)

1. `native/imt/` が R2 の制約下でビルドされ、R9.1 のテストが全て通る。
2. 一様マップで既存伝送と等価な挙動(R4.5)が確認できる。
3. 適合テスト(R9.2)の雛形が両リポジトリに存在する。
4. 本書の規範(R5, R6)からの逸脱がコードコメントではなく本書の改版として記録される。

## 11. 既知の制約・リスク

- **Pi 4 の v4l2h264enc は外部 QP マップを受けない**。ROI 実験は libx264 直叩き
  (`x264_picture_t.prop.quant_offsets`)のソフトウェアパスで行う。
  HW エンコード条件では imt の FEC・順序・pace のみ有効(ROI 無効)となる。
  実験条件表でこの差を明示すること。
- MAP の単一データグラム送信(R6.3)は MTU 超でフラグメントする。LAN 前提の
  割り切りであり、WAN 展開時はチャンク化への拡張が必要(version 繰り上げ事項)。
- 既存 `mpq_packet` とは独立の新フォーマットであるため、移行期間中は受信側で
  両ヘッダの magic 判別が必要。

## 12. 実装配置

- コア: `rp-stereocam/native/imt/`(`include/imt.h` + `src/imt_*.c` + `tests/`)
- 送信アダプタ: `stream_sender` から imt を利用(既存コードの置換はしない)
- 受信アダプタ: `MetaPuppetVR/native/pcvr_receiver` に imt ヘッダをベンダリング
- 本書が唯一の規範。受信側リポジトリには本書へのリンクのみ置く

## 13. トレース再生ハーネス(v0.2 追補)

ハードウェア・ネットワークなしで伝送特性(フレーム完成率・FEC回復・オーバー
ヘッド)を測る再現可能な評価ドライバ。トレース駆動ケーススタディ(遠隔操縦・
会議等)と論文 artifact の基盤。実体は `native/imt/tools/imt_trace_replay.c`
(C99 単体実行ファイル、依存は imt と libc のみ)。ツールであるため R2.3 の
浮動小数点禁止は適用しない(集計・表示に限り使用可)が、**決定性は必須**。

- **R13.1 入力**:
  - フレームトレース CSV: `frame_seq,size_bytes,capture_ts_ns`(`#` 行は
    コメント)。実映像からの生成方法(ffprobe 等)は本書の付録に書式例として
    記載するが、生成スクリプト自体はスコープ外。
  - ロスモデル(排他、いずれか1つ):
    `--loss-iid <ppm> --seed <n>`(独立同分布)、
    `--loss-ge <p_ppm>,<r_ppm>,<h_ppm>,<k_ppm> --seed <n>`(Gilbert-Elliott、
    無線バースト損失の標準モデル)、
    `--loss-trace <file>`(落とすパケット通し番号の明示リスト)。
    乱数は固定シードの LCG。`rand()` / OS 乱数は禁止。
  - 重み: `--weights uniform:<w>` / `--weights twolevel:<hi>,<lo>,<fr_q8>`
    (先頭 fr/256 のチャンクを hi に)/ `--map-file <file>`(cols,rows,
    tile_size ヘッダ+バイト列)。既定は uniform:128。
- **R13.2 処理**: 各フレームのペイロードは frame_seq 由来のシードで生成した
  疑似乱数列とし、packetize → ロス適用 → assembler → **ビット一致検証**まで
  を1パスで行う。
- **R13.3 出力**: フレーム毎 CSV
  `frame_seq,size,chunks,groups,packets_data,packets_parity,packets_lost,`
  `chunks_recovered,completed,bit_exact` と、サマリ行
  (completion_rate / recovery_contribution(パリティがなければ失われていた
  フレーム率)/ overhead_pct / 実効 goodput)。
- **R13.4 決定性**: 同一入力+同一シード → バイト同一の CSV。実時間・実時刻を
  出力に含めない。
- **R13.5 性能**: 平均 17KB × 10,000 フレームの再生が x86 で 10 秒以内。
- **R13.6 受け入れ**: (1) ロス 0 で completion_rate = 1.0 かつ全フレーム
  bit_exact、(2) 「各グループ1欠損」パターンで chunks_recovered が CSV に
  現れ completion_rate = 1.0、(3) 同一シードでの再実行で CSV が一致。

## 14. 受信側統合(v0.3 追補)

imt コアは「フレームの完全な再構成または棄却」までを保証し、復号は受信
アダプタ(`pcvr_receiver`)の責務とする。境界を保ったまま、以下を受信側の
統合要件として規定する。

- **R14.1 参照破壊の追跡**: フレーム棄却(`frames_incomplete` 増加)後、
  次のリカバリ完了までの間に復号されたフレームは「参照が汚染されている
  可能性あり」として扱えること。受信アダプタは棄却イベントからの経過
  フレーム数を保持し、統計(汚染疑いフレーム数)として公開する。
  送信側が intra-refresh の場合、リカバリ完了はリフレッシュ1周期
  (送信側設定値、MAP と同様に帯域外でなく flags/設定で受け渡す)とする。
- **R14.2 KEYFRAME_NACK による限定回復**: 受信アダプタは、不完全な
  キーフレームが新しいフレームに置換された時だけR6.4aのNACKを同じ送信元へ
  1回送る。同一受信epochの同じ`frame_seq`を重複要求しない。送信アダプタは
  最新キーフレーム1つだけを保持し、要求seqが一致し、かつ未再送の場合だけ
  1回再送する。再送後のNACK、古いseq、形式不正NACKは無視する。再送FECは
  全チャンクの正規化重み255(最小グループサイズ)とする。packetizerの
  スクラッチを複数スレッドから触らず、通常送信と同じ所有スレッドで再送する。
  受信assemblerはNACK機能を明示的に有効化した場合だけ、要求seq以後の
  interframeを一時的に棄却し、同seqの再送キーフレームまたは次の自然な
  キーフレームを回復点として受理する。これによりlatest-wins規則が再送を
  stale扱いすること、および参照フレーム欠落中のPフレーム復号を防ぐ。
- **R14.3 MAP の消費経路**: 受信アダプタは `imt_assembler_get_map` の
  結果を表示・衝突判定系へ受け渡せること。MetaPuppetVR では R8 テクスチャ
  として既存のレンダーイベント経路でアップロードし、
  `IMetaPuppetMaskSource` 実装(`MetaPuppetExternalMaskSource`)経由で
  供給する。MAP はヒントであり(R2.5)、映像フレームとの厳密な
  同期は要求しない(EMA 平滑化前提)。
- **R14.4 復号は imt の外**: ハードウェアデコード等の復号最適化は受信
  アダプタの実装事項であり、imt コアに復号・コーデック依存を持ち込まない。
